# Records the team can use

Prefer existing documentation, profile files, and trackers. These are the
fields the work needs, not a demand to create five new documents. A small
run can combine them in one report. For a new location, use `ds-ai-rails/`
in the agreed consuming project or shared configuration repository. Keep
credentials, sensitive settings, and unnecessary personal data out.

## Environment profile

Record the system and product, target user task, changed areas, purpose
(exploration/prototype/production), inspected AI surfaces, and permitted
operations. Link the authoritative sources and their owners per concern,
consumed versions, and any derived design/code/docs representations.

Include the ecosystem boundary, reuse posture, composition freedom, gap
routes, access paths and observed capability probes, existing checks,
release/review requirements, and feedback destinations. Mark unknowns and
the source/date of reported information. Update maintained profiles instead
of duplicating their catalog data.

## Assessment and plan

| Finding | Status | Evidence and scope | Consequence | Next useful change | Owner/role | Acceptance check |
|---|---|---|---|---|---|---|

Use working, partial, missing, not inspected, or not applicable for status,
and verified/reported/unknown for the evidence. Prioritize by what blocks a
useful pilot or undermines confidence, not by how many boxes are unchecked.
Name dependencies and actions the user can actually perform in their tool.

When using the techniques review, include applicable categories, relevant
study/upstream links and dates, local fit, maintenance burden, and the
acceptance exercise for each proposed change. A technique's presence is
separate from evidence that it helps. Record intentional exclusions without
penalizing the team for them.

## Team decisions and gap records

For each unresolved decision, capture:

- The concrete user need or example and the evidence that exposed it.
- Existing solutions checked, viable routes, and relevant tradeoffs.
- The current choice and status: settled, provisional, proposed, or unresolved.
- Scope, permitted work, work held for a decision, and authorization evidence.
- Decision owner, or an explicit ownership gap; review date or trigger.
- Destination or existing tracker link, and the next decision needed.

For an exception, add expiry/review conditions and an exit plan. For a
contribution, distinguish draft, filed, accepted, released, and adopted.
Link the tracker instead of maintaining a second backlog. When filing is
unavailable or unauthorized, label the record as a draft.

Example, to adapt rather than adopt automatically:

> **Provisional for the search-page prototype:** compose the filter bar
> from existing controls and tokens in the product's patterns directory.
> A new date-range primitive is held for the system owner. The product lead
> approved this prototype scope; production promotion requires review.
> The team still needs to decide whether reusable filter patterns belong
> locally or in its shared library. Revisit at the prototype review.

This makes progress possible without deciding the organization's entire
extension policy or giving the agent unlimited discretion.

## Setup changes

For each requested change, record the file/setting, concrete diff or setup
instructions, scope, rationale, activation state, required role, rollback,
and verification result. Link the actual command/tool definition where
appropriate. An instruction telling someone to enable a service does not
prove that service is enabled.

## Verification record

Record the brief, environment and versions, working policy revision,
run/session identifiers, date, repair budget, and evidence locations.
Include per-region provenance, API checks, runtime/render evidence, behavior
and accessibility results, system adherence, and human-review status.

List the negative fixtures, observed outcomes, and per-control enforcement
classification. Preserve failures, interventions, exceptions, comparison
differences, and unverified areas. Finish with the supported claim, such as:

> On this project's local agent, two runs used the installed component
> package and passed the exercised API and keyboard checks. A fabricated
> property was rejected. Release gating and human design review were not
> verified. The new date-range primitive remains held for a team decision.

Do not generalize that result to every model, consumer, or future run.
